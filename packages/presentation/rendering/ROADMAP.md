# Rendering Roadmap

[`../../../docs/roadmap-contract.md`](../../../docs/roadmap-contract.md) defines the normative roadmap schema and denominator review gate. [`../../../TERMINOLOGY.md`](../../../TERMINOLOGY.md) defines rendering, presentation state, render frame, visual parity, delivery status, coverage classification, inventory, and Complete.

## Completion Denominator

This leaf roadmap contains exactly 54 behavior rows with stable identities `REN-001` through `REN-054`. [`inventories/presentation-families.md`](inventories/presentation-families.md) indexes the same 54 identities and contributes no additional denominator identity. It is Candidate because no checked-in generator or denominator review exists. The current completion denominator is therefore exactly 54 items.

The target is one WebGPU rendering module for canonical Source 1 world data and presentation inputs from Team Fortress 2, Counter-Strike: Source, and legacy Source 1 Counter-Strike: Global Offensive. It owns browser GPU lifetime, immutable scene residency, presentation-only interpolation and model posing, view construction, draw preparation, pass ordering, pixels, submission, and frame-pacing records. WebGL, native graphics backends, editable scene formats, product UI, and authoritative gameplay or replay advancement are excluded.

The denominator is Not accepted. The inventory generator, accepted producer interfaces, declared browser/GPU evidence matrix, retained aligned captures, reviewer identity, review date, reviewed commit, and passing review record are Missing.

## Inputs

- One `RendererCreateRequest` containing an `HTMLCanvasElement` or `OffscreenCanvas` with no conflicting context mode; required adapter power preference; required WebGPU features and limits; canvas format, `srgb` color space, opaque or premultiplied alpha mode, and tone-mapping mode; `ldr` or `hdr` lighting profile; depth format; multisample count; and one complete `RenderingLimits` value. No field is inferred from game content, another renderer, or a failed device request.
- `RenderingLimits` contains non-negative finite integers for `maxCpuBytes`, `maxGpuBytes`, `maxSceneObjects`, `maxBuffers`, `maxBufferBytes`, `maxTextures`, `maxTextureBytes`, `maxTextureDimension2D`, `maxSamplers`, `maxShaderModules`, `maxPipelines`, `maxBindGroups`, `maxUploadBytesPerFrame`, `maxUploadOperationsPerFrame`, `maxPendingUploads`, `maxScenes`, `maxViewsPerFrame`, `maxPassesPerView`, `maxDrawItemsPerView`, `maxDrawsPerPass`, `maxTransparentItemsPerView`, `maxLightsPerView`, `maxBonesPerPose`, `maxParticleVerticesPerFrame`, `maxDiagnostics`, and `maxFramesInFlight`. Every operation uses the lower of the caller limit and the acquired device limit; no unbounded mode exists.
- One immutable `CanonicalMap` and map-root closure from `packages/world/map`, including Source-space geometry, displacement, brush-model, prop, decal/overlay, lightmap, cubemap, sky, fog, water, rope, and visibility references. Rendering never opens BSP bytes or assembles a second map representation.
- Immutable `ResolvedMaterial` and evaluated material state from `packages/world/material`; decoded texture planes and metadata from `packages/formats/vtf`; and immutable content-addressed bytes from the configured asset consumer. Rendering receives exact object hashes, byte lengths, dimensions, formats, mip/frame/face/slice identities, color interpretation, and sampling roles. It never resolves logical paths or interprets VMT syntax.
- Immutable `StudioModelDocument` values from `packages/formats/studio-model`, plus game-, Simulation-, or Replay-owned model occurrence state containing model identity, transform, selected skin, selected bodygroup values, selected sequence and cycle, playback parameters, pose parameters, flex inputs, attachment state, and discontinuity markers. Rendering does not select gameplay activities, items, weapons, models, sequences, skins, or bodygroups.
- One immutable visibility result per view from `packages/world/visibility`, containing ordered leaves, world-surface and static-, dynamic-, and detail-prop candidates, area windows, sky classification, map-occlusion decisions, bounds, model origins, and radii. Rendering owns frustum tests, distance/fade policy, LOD choice, draw grouping, GPU occlusion, and final draw decisions.
- Runtime-neutral Entity, game, Simulation, or Replay presentation state for dynamic transforms, render modes, modulation, light styles, dynamic lights, fog/controllers, water state, decals, ropes, beams, sprites, glows, and viewmodels. The selected game owns game-specific presentation mappings. `packages/presentation/particle` supplies immutable particle render data after particle advancement.
- One `RenderFrameRequest` containing a strictly increasing frame ordinal; finite presentation timestamp and interval; immutable previous and current authoritative snapshots; exact interpolation fraction in `[0,1]`; discontinuity set; ordered presentation events; active scene identity; 1 through `maxViewsPerFrame` cameras; viewport size; visibility results at matching state revisions; particle render data; debug-view selection; and capture request. A request cannot advance gameplay or replay.
- One optional `FramePacingRequest` containing a caller-selected foreground/background policy, maximum queued frame opportunities, and a browser animation-frame callback. It schedules presentation only; elapsed wall time never advances gameplay or replay inside Rendering.
- W3C WebGPU Candidate Recommendation Draft `https://www.w3.org/TR/2026/CRD-webgpu-20260714/`: initialization, device loss, resources, limits, bindings, pipelines, copies, command encoding, queues, canvas configuration/sizing/color, errors, and debugging.
- Valve Source SDK 2013 commit `88fa198fba3fb85d46d4c95018254693fdc3af0a`: `src/public/{ivrenderview.h,iclientrenderable.h,istudiorender.h,view_shared.h,cdll_int.h}`, `src/public/engine/{IClientLeafSystem.h,ivmodelrender.h}`, `src/public/materialsystem/{imaterialsystem.h,imaterial.h,imesh.h,itexture.h,materialsystem_config.h}`, and `src/game/client/{iviewrender.h,viewrender.h,viewrender.cpp,view.cpp,clientleafsystem.h,clientleafsystem.cpp,interpolatedvar.h,cdll_client_int.cpp,detailobjectsystem.h,detailobjectsystem.cpp,c_rope.h,c_rope.cpp,iviewrender_beams.h,view_beams.cpp,c_sprite.cpp,glow_overlay.h,glow_overlay.cpp,c_baseanimating.h,c_baseanimating.cpp}`.

## Outputs

- One `Renderer` interface with exactly `loadScene`, `render`, `resize`, `startFramePacing`, `stopFramePacing`, and `dispose`. Initialization is performed by `createRenderer`; device acquisition, caches, pass graph, encoders, queues, and recovery remain hidden implementation state.
- Lifecycle state exactly `Initializing`, `Ready`, `Recovering`, `Failed`, or `Disposed`; one monotonically increasing device generation; one optional active immutable scene generation; and a bounded queue of retiring generations. Only `Ready` accepts scene or frame work.
- A successful `loadScene` consumes one verified `MapRuntimeDescriptor` and returns an immutable scene identity, map-source identity, compiler/configuration identities, device generation, source/derived object closure, exact CPU/GPU resource ledger, upload ledger, handled or intentionally inert family classifications, and a frame-boundary activation token. Failure publishes no scene generation.
- A successful `render` writes the configured canvas image and returns a `FrameResult` containing frame and scene identities, interpolation inputs, ordered view/pass identities, candidate and draw counts, upload counts/bytes, submitted queue serial, resource totals, pacing record, capture identity when requested, and sorted diagnostics. Queue submission occurs exactly once after every encoder and pass for the frame has ended.
- `resize` returns the accepted physical width and height, viewport, device generation, and replacement attachment identities. Zero dimensions suspend submission without destroying immutable scene state. A dimension above the caller or device limit fails before canvas or attachment mutation.
- `dispose` stops pacing, rejects later work, unconfigures the canvas, destroys every explicitly destroyable owned GPU resource after submitted work is no longer using it, releases CPU scene data, and is idempotent. It never relies on garbage collection for predictable resource release.
- A structured error uses exactly `InvalidState`, `MalformedInput`, `MissingInput`, `IdentityMismatch`, `UnsupportedEnvironment`, `UnsupportedFeature`, `UnknownPresentation`, `BoundExceeded`, `GpuValidationFailed`, `OutOfMemory`, `DeviceLost`, or `CaptureFailed`. It records operation, renderer/device/scene/frame identity, family ID, offending value, required and available limit, GPU object label when available, and last successfully submitted queue serial.

## Invariants

- Rendering derives presentation state and GPU work only. It never mutates gameplay snapshots, Replay snapshots or cursors, Entity lifecycle, particle simulation state, canonical map/model/material values, or game-owned presentation mappings.
- Source positions remain Source XYZ and one-inch units in canonical inputs and immutable vertex buffers. View/projection matrices perform the Source-to-WebGPU clip transform exactly once. Instance, bone, attachment, light, fog, reflection, decal, and particle inputs use the same Source-space contract.
- A renderer owns exactly one canvas context and one live device generation. A GPU object belongs to exactly one device generation and is never reused after loss. Immutable CPU asset bytes survive recovery only while their scene lease remains live.
- GPU cache identity is `{deviceGeneration, objectSha256, semanticRole, descriptorSha256}`. Equal keys share one resource; unequal keys never alias. Scene activation and retirement change lease counts only at frame boundaries.
- Resource allocation, staging, upload, command encoding, draw-list insertion, diagnostics, and capture readback are charged before mutation. A bound failure emits no partial scene, pass, command buffer, or submitted frame.
- Scene loading resolves only the exact supplied object closure. Missing, hash-mismatched, malformed, unsupported, or unknown required input fails the scene. Rendering never substitutes placeholder geometry, texture, material, model, light, or effect.
- Device loss stops new encoding and submission, marks every GPU object unusable, drains no assumption about unfinished work, and enters `Recovering`. Recovery reacquires the same required profile and rebuilds leased scenes from immutable inputs. Capability mismatch or rebuild failure enters `Failed`; no reduced profile is selected.
- Every draw item has stable scene, view, family, occurrence, material, mesh, and source identities. Opaque batching may change command count but not depth, stencil, blend, modulation, material evaluation, or pixel results. Equal-key ordering uses stable identities, never host map order or asynchronous completion order.
- Visibility output is candidate input, not a draw command. Rendering may remove candidates only through the declared view frustum, area window, distance/fade, LOD, map-occlusion, GPU-occlusion, material, and debug policies. It cannot add a world candidate excluded by the matching visibility result.
- Opaque and alpha-tested draws establish depth before translucent interleaving. Translucent world surfaces, displacement surfaces, detail props, particles, ropes, beams, sprites, glows, and entities are interleaved back-to-front by visibility-leaf order and the family-specific stable tie rules. Ignore-depth draws execute only in their terminal declared phase.
- Each auxiliary view has its own camera, visibility result, render targets, fog, clip state, draw flags, and pass results. State pushed for shadow, reflection, refraction, 3D-sky, debug, or viewmodel work is restored before the next view.
- Presentation interpolation uses only the supplied snapshot pair, fraction, per-field policy, and discontinuities. It never extrapolates, smooths across create/delete/teleport/seek/reset, reads wall-clock state, or writes interpolated values back to authority state.
- One render frame performs immutable-input validation, interpolation and pose evaluation, view derivation, candidate pruning and sorting, bounded upload work, auxiliary passes, main opaque/depth work, main translucent work, viewmodels, color output, diagnostics/capture, command finalization, and one queue submission in that order.
- Color textures declare data or color interpretation. Lighting and blending execute in linear light; final output applies the selected LDR or HDR presentation and one declared transfer to the configured canvas color space. A texture is never decoded as sRGB merely because its bytes are RGBA8.
- Diagnostic and capture modes may replace presentation shaders or emit ID/depth/lightmap outputs, but cannot alter canonical state, resource identity, candidate enumeration, or subsequent ordinary frames.

## Ownership Exclusions

- BSP, VMT, VTF, StudioModel, particle-definition, and other Source-format byte parsing belongs to `packages/formats/*` and `packages/presentation/particle` where declared.
- Canonical geometry, occurrences, map sections, dependency closure, environment associations, and runtime descriptors belong to `packages/world/map`. Rendering owns only derived GPU buffers, atlases, draw items, and pixels. It accepts browser-WASM or native-precomputed data under the same derived identities and never requires GLB.
- Shader, parameter, proxy, texture-role, animation-frame, blend, depth, cull, lighting-model, water, sky, and decal material semantics belong to `packages/world/material`. Rendering owns GPU implementation of the supplied semantic state.
- PVS/PAS expansion, BSP and area traversal, portal windows, map occlusion, leaf membership, and ordered visibility candidates belong to `packages/world/visibility`.
- Entity lifecycle, hierarchy, I/O, controller transitions, rope state, and generic effect requests belong to `packages/world/entity`; gameplay and game-specific model/effect/sequence selection belong to `games/<game>`.
- Gameplay advancement and snapshots belong to Simulation and the selected game/ruleset. Recorded-state advancement, seeking, snapshot selection, and replay events belong to Replay. Rendering consumes immutable presentation inputs from either authority.
- Particle definitions, emitters, operators, state advancement, and runtime-neutral particle render data belong to `packages/presentation/particle`. Rendering owns only particle draw preparation, ordering, GPU resources, and pixels.
- Product routes, controls, focus, overlays, accessibility, browser support policy, and product-specific camera selection belong to applications. Rendering owns camera mathematics and submitted views after selection.
- Asset retrieval, object storage, publication, CDN behavior, and browser HTTP caching belong to Content, Asset Store, services, and applications. Rendering consumes supplied immutable bytes and owns their GPU residency only.
- Inventory and capture command orchestration belongs to `tools/playsrc` and `tools/inspector`.

Schema 4 validates the complete `PSHD` version-1 descriptor, recomputes its member closure and retained VTF hashes, preserves linear sample radiance in binary32, composes all supplied light-style layers, constructs flat plus three directional float atlases, and exposes official-basis normal and direct-coefficient SSBump evaluation. World-light and leaf-ambient records remain typed lighting inputs, while model-to-leaf state, decoded sky resources, complete Water associations/state, and current controller state remain `Missing` or `Unsupported` requirements. Renderer/device and scene generations own cancellation, atomic replacement, loss recovery, resize suspension, capture, queue-safe retirement, and idempotent disposal.

[`EVIDENCE.md`](EVIDENCE.md) records the deterministic unit vectors, exact schema-3/schema-4 `jump_beef` counts and hashes, raw/quantized radiance boundaries, Chrome WebGPU profile, fixed-camera capture hashes, replacement generations, and post-disposal canvas state. The HDR capture is diagnostic because required SSBump, sky, water, environment, and model-material producer inputs remain unavailable; it makes no visual-parity claim.
