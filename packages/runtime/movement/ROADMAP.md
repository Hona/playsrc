# Movement Roadmap

[`../../../docs/roadmap-contract.md`](../../../docs/roadmap-contract.md) defines the normative roadmap schema and denominator review gate. [`../../../TERMINOLOGY.md`](../../../TERMINOLOGY.md) defines delivery status, coverage classification, inventory, and completion terms.

## Completion Denominator

This leaf roadmap contains exactly 36 behavior rows. The candidate inventory contains 101 generic movement-mode, toss-response, configuration, policy-input, limit, threshold, factor, distance, and timer items in [`inventories/modes-and-parameters.md`](inventories/modes-and-parameters.md). It contributes 0 denominator items until a checked-in generator emits it and a denominator review accepts it. The current completion denominator is therefore 36 behavior rows. Acceptance of all 101 candidate inventory items without a roadmap change would make the denominator 137 items.

The denominator covers generic Source player movement for one simulation tick: canonical movement-command interpretation; button transitions; command and absolute view angles; wish velocity; effective speed; constraints; standing, crouched, and observer hull selection; duck transitions; ground and surface classification; ground identity; friction; ground and air acceleration; jump latching; gravity; falling and landing; base velocity; conveyors; linear and rotational moving-ground carry; steps; slopes; walls; crease motion; stuck recovery; initial overlap; water levels, currents, swimming, and ledge exit; ladders; noclip; generic observer modes; toss motion; collision-query requirements; deterministic authority/prediction output; numerical policy; and classified failure. Game-selected values and game-specific movement decisions remain outside this denominator.

The denominator is Not accepted. The candidate inventory has no generator or review record; the current collision query contract is not accepted; and deterministic arithmetic and parity tolerances are undecided. Incremental stuck recovery now requires an explicit monotonic clock query, while client-world recovery retains the exact immediate 54-offset path. Generic fly custom and slide responses are `Unsupported` because the pinned handler delegates custom mutation to touch code and has no slide case.

## Inputs

- One immutable prior `MovementState`: stable player identity; Source-space origin, velocity, base velocity, local and command angles; move type and toss collision-response type; standing, crouched, transition, ladder, ground, water, falling, and stuck state; prior movement-button bits and prior forward command; ground identity and its immutable transform and linear/angular velocity; surface identity and movement properties; movement timers; model scale; health/alive and movement-enable predicates; and the collision snapshot identity used by the step.
- One canonical `MovementCommand`: non-negative safe command number and tick count; finite command and absolute view angles; finite forward, side, and up movement; movement-relevant button bits; and a first-execution marker. Networking owns decoding, ordering, acknowledgement, and transport. Simulation owns command admission and tick scheduling. The selected game owns command changes caused by classes, conditions, items, weapons, teams, and game rules before the generic step.
- One immutable `MovementConfiguration` containing every accepted movement-owned item in [`inventories/modes-and-parameters.md`](inventories/modes-and-parameters.md). Game-owned hull values, view offsets, effective maximum speed, air-speed cap, collision policy, jump policy, and movement modifiers enter through explicit validated values or pure policy results; Movement owns their generic consumption order.
- One positive finite fixed tick interval, one non-negative safe simulation tick, and one immutable simulation-time value. A movement step never reads render time, process time, network arrival time, or an ambient mutable cvar registry.
- One immutable collision snapshot and pure query interface supplied by `packages/world/collision`: exact point-contents queries; zero-motion standing/crouched/observer hull tests; swept hull traces; world/entity hit identity; fraction; end position; valid plane normal; surface identity and properties; contents; `startSolid`; `allSolid`; and the snapshot identity on every result.
- One ordered mover input supplied through entity/simulation coordination: requested old and new transforms, linear and angular velocity, hierarchy identity, blocking policy, and collision snapshot revisions before and after the request. Movement does not advance the mover clock.
- Valve Source SDK 2013 commit `88fa198fba3fb85d46d4c95018254693fdc3af0a`: `src/public/const.h`; `src/game/shared/igamemovement.h`, `gamemovement.{h,cpp}`, `imovehelper.h`, `movevars_shared.{h,cpp}`, `usercmd.{h,cpp}`, `in_buttons.h`, `shareddefs.h`, and `baseplayer_shared.{h,cpp}`; `src/game/server/player_command.cpp`, `player.cpp`, and `physics_main.cpp`; and `src/game/client/prediction.{h,cpp}`.
- The same SDK commit's `src/game/shared/tf/tf_gamemovement.cpp` and `tf_gamerules.cpp`, `src/game/server/tf/tf_playermove.cpp` and `tf_pushentity.cpp`, and `src/game/client/tf/tf_prediction.cpp` establish the generic/TF2 ownership seam. TF2 rows belong to `games/tf2/ROADMAP.md`.

## Outputs

- One immutable `MovementStepResult` containing the complete next `MovementState`: origin; velocity; base velocity; local and command angles; move mode; selected hull state; crouch fraction and timers; ground identity and surface state; ladder normal; water level and contents; water-jump state; fall velocity; stuck-sequence state; and prior-button state for the next command.
- Exact movement observables equivalent to the generic move-data outputs: accumulated wish velocity, jump velocity, and climbed step height.
- One stable ordered contact list. Each contact contains the collision snapshot identity, hit identity, trace result, impact velocity before clipping, and first-contact order; duplicate hit identities have one declared disposition.
- One stable ordered movement-event list containing only generic facts: jumped, landed with pre-impact speed, entered or left water, changed ground, climbed a step, attached to or detached from a ladder, became trapped, recovered from initial overlap, and requested a footstep or impact presentation. Games decide damage, class state, animation meaning, and game events; presentation and audio consume effect requests.
- One mover result containing accepted player displacement, resulting support/base velocity, blocker identity when blocked, and exactly one `moved`, `blocked`, or `crushed` classification. Entity/simulation owns mover acceptance, rollback, I/O, and damage requests.
- A structured failure containing operation, simulation tick, command number, player identity, collision snapshot identity, stable input field or query identity, violated invariant, offending value, configured limit, and exactly one `Malformed`, `Unsupported`, `Unknown`, or `Missing` classification. Failure publishes no next authoritative movement state.

## Invariants

- All positions, velocities, accelerations, hull bounds, distances, and plane normals use Source XYZ coordinates and inches. Angles use degrees. Tick durations and configuration units are explicit; millisecond timers are never compared directly with seconds.
- One step is a pure deterministic transition over the declared command, prior state, configuration, mover inputs, and one immutable collision snapshot. Authority and prediction invoke the same implementation and receive byte-identical serialized results for identical inputs on an accepted arithmetic profile.
- Command ingestion derives pressed and released bits from current and prior button sets exactly once. A held jump cannot create another ground jump until release; a failed generic air attempt and a game-rejected attempt retain their separately declared latch outcomes.
- Command view angles produce the forward/right/up basis used by movement. Absolute view angles are retained separately for parented state. Body/local angle output, view roll, and game-owned angle restrictions never overwrite the command basis retroactively within the same step.
- Movement applies speed selection in one declared order: game/player maximum, client maximum when nonzero, surface maximum-speed factor, outward movement-constraint factor, command-vector clamp, mode-specific wish-speed clamp, and game-owned post-policy where declared. A selected game cannot bypass generic finite-value or maximum-velocity validation.
- Standing, crouched, and observer hulls retain their supplied mins/maxs and model scale. Ducking changes collision hull, origin, view offset, timers, and command scaling as one state transition; a failed unduck retains the crouched hull and a deterministic retry state.
- Ground exists only after a movement-filtered hull trace returns an accepted hit with a standable plane. The full hull is checked before the four declared quadrant hulls. Ground identity, surface identity, surface friction, and base-velocity transition are changed atomically.
- Ground friction is applied before adding base velocity. Ground and air acceleration project current velocity onto normalized wish direction, add no speed when the projected speed already meets the applicable wish speed, and apply surface friction only where the selected generic formula requires it.
- Gravity uses the accepted effective gravity and player scale. Walk movement applies the two half-tick gravity contributions around horizontal/air movement; water-jump and mode rules explicitly suppress or replace gravity. Every gravity path is followed by maximum-velocity validation.
- Collision resolution performs no more than the accepted bump and clipping-plane limits. It consumes the remaining tick fraction after each hit, clips against every accumulated plane, uses the normalized cross product only for an exactly two-plane crease, and stops rather than moving opposite the primal velocity.
- Step movement evaluates low and high routes from the same prior origin and velocity. Only a route ending on standable ground is eligible. The accepted route-selection tie rule and retained vertical-velocity component are observable and game specialization may replace them only in the selected game.
- `startSolid` invokes the accepted deterministic recovery sequence or returns a trapped result. `allSolid` immediately prevents authoritative displacement and zeroes movement velocity according to the active mode. Neither flag is inferred from a miss or broad-phase overlap.
- Water level is exactly not-in-water, feet, waist, or eyes and is derived from declared hull-relative samples. Water contents and current bits remain unsigned 32-bit values. Current contribution, water friction, swim wish velocity, jump-up velocity, and ledge-exit state are applied exactly once per tick.
- Ladders attach only after a movement-filtered hull query identifies ladder contents or a climbable surface within the accepted distance. Ladder motion, jump-away, gravity suppression, and detach state are deterministic; the selected game may disable ladders or supply specialized policy.
- Noclip displacement invokes no collision query; the common prepass can still run target-required water and ground categorization. Observer follow modes copy one supplied target snapshot; fixed modes do not advance position; roaming selects clipped or noclip behavior from explicit configuration. Toss modes never become rigid-body simulation.
- Generic movement emits facts and requests but never mutates health, weapons, classes, conditions, objectives, rulesets, audio, particles, rendering, or mover entity state. Falling, drowning, crushing, and impact damage are selected-game or simulation consumers of movement output.
- Query caches, allocation addresses, worker schedules, broad-phase order, rendering frames, and prediction replay count never affect public movement output. A cache hit and miss over the same collision snapshot produce identical state, contacts, and events.
- Every scalar, vector, angle, bitset, timer, count, identity, hull, transform, query result, and intermediate arithmetic result is finite and within accepted limits before it can enter authoritative output. No fallback movement path, collision sampler, compatibility schema, or legacy state is permitted.

## Ownership Exclusions

- Networking owns user-command encoding/decoding, transport, acknowledgement, queues, backpressure, snapshots, and reconciliation. Simulation owns command admission, fixed-tick scheduling, pre/post-game ordering, state publication, and gameplay authority. Movement interprets exactly one admitted command for one scheduled tick.
- `packages/world/collision` owns collision geometry, contents/mask values, filtering execution, point contents, hull sweeps, overlaps, hit selection, trace fields, and query acceleration. Movement chooses query sequence and interprets returned movement facts without redefining collision.
- `packages/world/entity` owns entity state, parenting, mover requests, mover lifecycle, trigger/touch lifecycle, I/O, rollback publication, and crush dispatch. Movement owns player displacement induced by accepted linear/rotational mover input, support carry, base velocity, and the player-side blocker result.
- `packages/runtime/physics` owns rigid bodies, persistent contacts, constraints, sleeping, restitution, and solver response. Player walk, ladder, water, noclip, observer, and toss movement do not become rigid bodies.
- Each game owns hull and view values, maximum-speed derivation, collision masks/groups, air-speed-cap overrides, jump eligibility and impulse overrides, class/condition/item/weapon movement, fall and drowning damage, game events, and movement differences. TF2 owns air dashes, bunnyhop cap, backward-speed clamp, parachutes, grappling hooks, charges, stuns, taunts, karts, ghosts, lost footing, TF2 duck restrictions, team/buildable collision, disabled ladders, TF2 water sampling, and escort pusher policy.
- Each game-owned ruleset owns mode lifecycle and restrictions, including whether a TF2 ruleset selects escort pusher behavior, noclip permission, observer permission, spawn movement locks, or course/timer interaction.
- Material owns surface-property meaning. Movement consumes validated surface friction, maximum-speed factor, jump factor, material identity, and climbable state. Audio/presentation owns actual footstep, splash, landing, and impact effects.
- Weapons, explosions, trigger pushes, teleports, and game abilities own the impulses they request. Movement consumes explicit base-velocity or impulse inputs at the declared tick boundary and cannot originate those game decisions.
- Source 2 movement, vehicle driving, NPC locomotion, animation root motion, camera smoothing, render interpolation, replay resimulation, and product input bindings are excluded.

## Behavior Families

The active movement-parity checkpoint covers every target-reachable generic transition selected by the current Movement contract: command and absolute-angle state, speed-factor and annular constraints, button/latch state, standing/crouched/observer hull selection, reversible crouch, ground/surface/base-velocity transitions, conveyors, walk/air acceleration, jump, split/full gravity, falling/landing, low/high steps, slope/wall/multi-plane collision, exact stuck schedules, water levels/currents/swim/ledge exit, ladder attach/motion/detach, noclip, observer fixed/follow/roaming modes, fly/fly-gravity default/bounce response, and player-side linear/rotational mover displacement. A separate bounded linear-pusher producer now advances Entity-owned requests through immutable Collision snapshots and emits trajectory, completion, rollback, blocker-contact, carry, and support/base-velocity facts. Fixed tick traces expose position, velocity, wish direction/speed, support, selected hull, crouch fraction/view, ordered queries/contacts/events, and mover result. TF2 values and specializations remain game-owned; custom and slide fly responses remain categorically unsupported unless authoritative behavior establishes a pure generic contract.

The checkpoint retains the existing TF2 walk/noclip integration while replacing Movement's selected-mode approximations. Exact generic modes that excluded producers do not yet select remain implemented and tested at the Movement seam; this assignment does not add compatibility readers or duplicate adapters in TF2, Entity, Simulation, Collision, applications, or manifests.

The active TF2 combat/entity-automation integration consumes the existing linear-pusher producer without changing its authority: Entity supplies each current request, Movement returns progress/completion/block contacts plus subject carry/support/base velocity, and TF2 returns those facts to Entity before the next admitted player command. A completion output or blocked reversal may create a replacement request in that same Entity phase; that request remains pending until Movement consumes it and is never converted into game-owned displacement math.
