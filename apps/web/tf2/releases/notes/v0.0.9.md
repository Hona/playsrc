# playsrc v0.0.9

This update turns 2Fort practice into a complete 24-player local match, fixes actual Engineer building placement, prevents intermittent team/class-selection crashes, and adds a working set of Source-style video quality controls.

It also substantially reduces browser rendering work on `jump_beef`, `pl_upward`, and `ctf_2fort`: the latest headed Upward capture reduces GPU submissions from roughly 14 to 5 per completed frame, removes runtime pipeline-compilation hitches, preserves every authored prop, and keeps real 24-player 2Fort gameplay above 60 displayed frames per second.

## Local Matches and Classes

### Full 24-Player 2Fort Training Matches

2Fort now supports a complete local 24-slot Capture the Flag match with one human player and 23 real bots.

The local player's team contains the player and 11 bots; the opposing team contains 12 bots. Both RED and BLU therefore retain exactly 12 active players rather than displaying invented scoreboard entries or silently exceeding the authored player limit.

Bots join through the actual Create Server quota manager, preserve Source team balancing and admission cadence, spawn in their authored team rooms, navigate the configured 2Fort mesh, fight, reload, take damage, die, respawn, collect supplies, and participate in intelligence objectives. All nine playable class identities and their available stock equipment remain supported.

The first full-roster headed verification sustained 67.86 simulation ticks per second with 16.665 ms median and 18.66 ms 95th-percentile displayed-frame intervals. Reordered particle batches reduced GPU buffer creation from 21,463 to 4,729 in the observed full-match scenario.

The final integrated renderer capture retained all 23 bots, completed 306 genuinely rendered gameplay frames in five seconds, reached 61.2 actual displayed frames per second, and sustained 68.11 simulation ticks per second.

Related pull request: [#131](https://github.com/Hona/playsrc/pull/131).

### Working Engineer Construction and Upgrades

Engineer buildings can now be placed through ordinary gameplay: select the construction PDA, choose a Sentry Gun, Dispenser, Teleporter Entrance, or Teleporter Exit, move onto valid authored ground, and use a real left mouse click while native Pointer Lock remains active.

The prior headed check issued `+attack` through the developer console and could use noclip, allowing the automated scenario to pass while ordinary physical mouse placement remained broken. The corrected implementation verifies actual team/class menus, authored building menus, ordinary walking, native mouse input, blueprint validity, visible building models, and the resulting metal cost.

Authored `func_nobuild` volumes, active respawn rooms, team filtering, per-building allowances, player-clip traces, collision hulls, and valid placement surfaces remain enforced. BLU single-skin teleporter blueprints now render correctly, and wrench upgrades consume the correct available metal instead of only changing decorative state.

A visibly headed RED Upward and BLU 2Fort scenario successfully placed all eight team/building combinations, observed 168,522 real building pixels, reduced upgrade metal from 70 to 45, and sustained 67.13 simulation ticks per second.

Related pull request: [#132](https://github.com/Hona/playsrc/pull/132).

### Team and Class Selection No Longer Crashes

Selecting a team or class after changing maps no longer intermittently terminates gameplay with `Bot(MissingScenario)`.

The previous Create Server path retained valid bot settings between map generations and submitted them unconditionally to `jump_beef`, even though that map has no authored navigation mesh or bot scenario. Coalesced Worker commands could surface the resulting Rust error while the player was selecting RED, BLU, or a class.

Bot configuration, difficulty changes, and quota commands now enter simulation only when the current map generation actually owns its authenticated navigation data. The fix preserves strict errors for genuinely invalid bot requests and retains complete bot behavior on `ctf_2fort` and `pl_upward`; it does not invent navigation for the jump map.

Headed regression coverage exercises persisted practice settings across `jump_beef`, `ctf_2fort`, `pl_upward`, and a final return to `jump_beef` using real team/class admission and visible rendered pixels.

Related pull request: [#128](https://github.com/Hona/playsrc/pull/128).

## Video Settings and Rendering

### Balanced Source Video Advanced Defaults

Fresh browser sessions now use one coherent Source-style Video Advanced configuration shared by the Options interface, console variables, persisted settings, map preparation, WebGPU texture uploads, and renderer replacement.

The default preset is:

- Model detail: Medium, `r_rootlod=1`.
- Texture detail: Medium, `mat_picmip=1`.
- Shadow detail: Medium, `r_shadowrendertotexture=1` and `r_flashlightdepthtexture=0`.
- Shader detail: Low, `mat_reducefillrate=1`.
- High-dynamic-range rendering: Off, `mat_hdr_level=0`.
- Antialiasing: Disabled, `mat_antialias=0` and `mat_aaquality=0`.
- Texture filtering: Bilinear, `mat_trilinear=0` and `mat_forceaniso=1`.
- Water detail: No reflections, `r_waterforceexpensive=0` and `r_waterforcereflectentities=0`.
- Multicore rendering: Enabled, `mat_queue_mode=-1`.
- Color correction and motion blur: Disabled.

The settings owner translates selections in both directions, so model detail, texture detail, shadows, shaders, HDR, bilinear/trilinear/anisotropic filtering, supported antialiasing, and water choices remain consistent with their corresponding Source console variables. Authored VTF mip selection and sampler filtering affect actual GPU uploads instead of only changing menu labels.

Renderer-affecting changes use atomic owner transactions, persistence, and live renderer/map replacement. Supported antialiasing uses actual WebGPU sample configurations. Browser-controlled vertical synchronization is reported truthfully as unavailable because WebGPU does not expose a browser compositor swap-interval control; the UI does not pretend that it can disable display synchronization.

A headed three-map run at 1280x720 used the single-sample default, preserved HDR/LDR replacement and authored gameplay, sustained more than 66 simulation ticks per second, and measured 16.665/17.805/18.645 ms displayed-frame p50/p95/p99 with zero GPU validation errors.

Related pull request: [#137](https://github.com/Hona/playsrc/pull/137).

### Stable Authored Animated Textures

Animated world and water textures retain their original authored frames across repeated playback cycles instead of repeatedly destroying and recreating active GPU textures during normal movement.

A six-second visibly headed Upward grounded-walking capture reduced GPU texture creation from 198 to 40, a 79.8% decrease, while the final capture reported zero prematurely destroyed textures or buffers.

The same run preserved actual collision-based walking, native pointer input, the authored 3D sky, static props, first-person weapon, water, HUD, and 69.15 simulation ticks per second. It produced 354 genuinely completed frames, or 58.98 displayed frames per second on the actual approximately 60 Hz display.

The later quality-settings implementation also defers GPU resource disposal until the submitted work that references those resources has completed. This prevents destroyed-texture validation errors without blocking ordinary gameplay frames on a global GPU fence.

Related pull requests: [#133](https://github.com/Hona/playsrc/pull/133) and [#137](https://github.com/Hona/playsrc/pull/137).

### Synchronized 3D Sky Cameras

The authored 3D sky now moves and turns with the same immutable presentation camera used by the main world instead of visibly updating on a stale or independent cadence.

For each completed gameplay frame, the sky position follows the configured Source transform `skyOrigin + worldPosition / skyScale`; sky yaw, pitch, field of view, viewport generation, and presentation revision remain coherent with the displayed world. Late asynchronous visibility responses are rejected before GPU submission rather than mixing one frame's sky with another frame's world.

Upward retains its authored sky origin `[7168, -2048, 0]`, scale `16`, area `1`, and original fog. Controller-absent maps continue to behave correctly without manufacturing a sky camera.

A headed grounded movement and continuous pointer-motion scenario verified 369 coherent completed sky/world frames, 92 distinct camera orientations, 530 units of real movement, 67.33 simulation ticks per second, and actual distinct visible sky pixels. The complete profiled operation took 21.64 seconds, including startup, map loading, the five-second active capture, and cleanup.

Related pull request: [#134](https://github.com/Hona/playsrc/pull/134).

## GPU Performance

### Fewer WebGPU Submissions and No Runtime Pipeline Hitches

World, 3D sky, water, viewmodel, and HUD model rendering now share one ordered linear framebuffer path. Authored depth resets are folded into the following render pass, and the final output color conversion occurs once rather than introducing additional independent GPU work.

Reachable world, sky, static-prop, dynamic-model, and water pipeline variants are compiled before interactive exposure. Reflection and refraction targets are allocated only when the actual authored non-cheap water material requires them.

The final headed Upward capture recorded 1,474 genuine queue submissions across 293 completed gameplay frames, or 5.03 submissions per frame compared with the earlier 14.03-submission baseline. Completed render workload measured 2.175/2.860/3.495 ms p50/p95/p99, with a 9.635 ms maximum, zero runtime pipeline creations, 167.3 MB of renderer GPU memory, and 69.43 simulation ticks per second.

The complete Upward profiling command took 20.182 real seconds from invocation through teardown. A separate full 24-player 2Fort capture completed in 29.647 seconds, retained all 23 bots, rendered 306 actual frames in five active seconds, and preserved the authored sky.

No quality mode, map geometry, Source simulation cadence, water pass, player model, browser context, or required depth ordering was removed to obtain these results.

Related pull request: [#141](https://github.com/Hona/playsrc/pull/141).

### Persistent World and Sky Render Bundles

Main-world and authored 3D-sky geometry now retain independent persistent WebGPU render bundles while visibility changes update bounded indirect draw state and only the required index data.

Walking through new potentially visible sets no longer rerecords the complete world bundle on every ordinary camera movement. Main/sky isolation, ordered Source face selection, translucent/decal ordering, stale map-generation rejection, and authored visibility remain intact.

A five-second headed Upward traversal completed 375 gameplay frames at 68.22 simulation ticks per second with zero render-bundle rebuilds, invalidations, GPU validation failures, or lost contexts. Measured GPU queue-write volume fell from 527.7 MB to 66.0 MB for the verified traversal.

Related pull request: [#140](https://github.com/Hona/playsrc/pull/140).

### Static Props Batched Without Losing Authored Lighting

Compatible opaque static props are now grouped into Source-sized batches while retaining each original occurrence's transform, model, skin, selected level of detail, visibility, main-world/sky ownership, and individual authored baked vertex lighting.

On 2Fort, 1,933 of 2,265 authored props join 263 compatible batches, reducing the active scene hierarchy from 2,265 occurrence groups to 622 attached nodes. On Upward, 558 of 1,244 authored props join 109 compatible batches, reducing the hierarchy to 795 nodes.

No authored prop is removed, and differing VHV lighting is not flattened into an invented shared color. Headed 2Fort verification preserves all 23 match bots, 67.7 simulation ticks per second, an 18.5 ms displayed-frame 95th percentile, approximately 168 MiB of resident textures, and 253,383 authored sky pixels.

Related pull request: [#139](https://github.com/Hona/playsrc/pull/139).

### Persistent Player, Viewmodel, and Particle Buffers

Dynamic player, bot, viewmodel, HUD-model, and particle geometry now retains persistent GPU buffers and uploads only the exact changed binary32 position, normal, tangent, and particle data.

Pose comparison preserves signed zero and NaN payload identity rather than guessing that visually similar animation states are interchangeable. Ordered sprite/trail geometry, blend modes, authored particle depth, model attachments, viewmodels, and all 24 active players remain intact.

A visibly headed six-second full-roster 2Fort run completed 350 actual frames at 58.33 displayed frames per second and 67.64 simulation ticks per second. Compared with the preceding full-roster capture, GPU buffer creation fell from 14.82 to 11.43 per completed frame, queue submissions fell from 15.20 to 13.15 per frame, and displayed-frame p95 improved from 18.66 to 17.665 ms.

The capture retained 133,776 exact posed-attribute observations, 83 reusable particle batches, 884,536 visible authored outdoor pixels, and 251,729 authored sky pixels. GPU byte counters were corrected in this release, so the new accurate upload totals are not incorrectly compared with older undercounted measurements.

Related pull request: [#136](https://github.com/Hona/playsrc/pull/136).

## Diagnostics and Frame Pacing

### FPS Now Counts Completed Gameplay Frames

`cl_showfps` now updates after a gameplay frame actually finishes rendering rather than counting every browser `requestAnimationFrame` callback.

The prior discrepancy could report approximately 165 browser callbacks per second while only 47.8 complete gameplay frames were presented. The corrected counter reports the observable world-rendering cadence; position diagnostics still update independently when the FPS display is disabled.

Related pull request: [#130](https://github.com/Hona/playsrc/pull/130).

### Accurate Multi-Pass GPU and Stall Instrumentation

Optional performance capture now measures one complete displayed gameplay frame across all sky, water, world, viewmodel, HUD, and compute passes instead of resetting renderer counters between individual passes.

The profiling contract records actual completed frames, separate browser callback counts, per-pass draw calls and queue submissions, texture/geometry/uniform GPU memory, buffer and texture creation, render-pipeline misses, render-bundle encodes, upload bytes, Worker queue pressure, camera revisions, and available hardware GPU timestamp queries.

Supported browsers additionally expose Long Animation Frames attribution for script and rendering stalls. Heavy profiler data remains structured and opt-in, avoiding per-frame JSON serialization and DOM attribute churn during ordinary gameplay.

A headed grounded Upward run observed 291 genuinely completed frames, 58.1 displayed frames per second, 68.1 simulation ticks per second, nine actual GPU timestamp samples, and zero GPU validation errors. The entire command completed in 20.7 seconds.

Related pull request: [#138](https://github.com/Hona/playsrc/pull/138).

## Loading and Development

### Portable Authenticated Navigation Meshes

Development installations no longer require their locally generated Upward or 2Fort navigation mesh to match an unrelated machine's hardcoded byte-for-byte NAV hash.

The configured mesh is authenticated using the shared Source NAV parser, exact map BSP size and content build, supported TF2 format, world bounds, connected RED/BLU spawn areas, and the relevant intelligence or authored payload route. The actual local mesh SHA-256 and provider provenance remain part of the immutable source graph; malformed, wrong-map, out-of-bounds, disconnected, or symlink-escaping content is rejected.

The complete production release still prepares and verifies all three configured map closures, while local development can accept legitimately generated authenticated NAV data for the same declared map.

Related pull request: [#135](https://github.com/Hona/playsrc/pull/135).

### Faster Targeted Development Startup

Local development now initially prepares only the selected map instead of always acquiring, compiling, and publishing all three configured maps before exposing the development server.

Other maps are prepared and activated lazily through authenticated replacement catalogs when a real map switch occurs. Cached bundles remain keyed by the actual producer, configured content root/build, BSP, target, and selected local NAV SHA-256.

Observed cold targeted 2Fort startup improves from approximately 89 seconds to 51.97 seconds. Warm complete startup improves from 0.33 to 0.26 seconds while preparing one map rather than three. A warm headed `jump_beef` to `pl_upward` and back operation completes in 55.58 seconds with 9.92 seconds of lazy Upward preparation.

Setup accepts compatible Bun 1.4.0 executable revisions instead of demanding one machine-specific revision. Its observed 128 ms setup still verifies exact Rust, Cargo, rustup, threaded toolchain, WASM targets, required components, and wasm-bindgen versions.

Related pull request: [#135](https://github.com/Hona/playsrc/pull/135).

## Additional Fixes

- Preserve authored model/particle buffer contents when a pose changes only by a binary32 signed zero or NaN payload.
- Reject stale asynchronous sky visibility without publishing mismatched camera revisions.
- Keep static-prop visibility and baked lighting distinct between main-world and 3D-sky render bundles.
- Retain original animated world and water texture frames without destroying textures still referenced by submitted GPU commands.
- Avoid allocating reflection or refraction targets when the authored selected water mode does not require them.
- Maintain physical Pointer Lock across ordinary Engineer attack clicks and building rotation.
- Keep the held scoreboard, intelligence HUD, class selection, health/ammunition panels, and 24-player rows synchronized with authoritative match state.
- Record actual command startup, lock acquisition, map readiness, active sampling, and teardown rather than hiding development wait time.

## Current Scope

- Gameplay remains local single-player and bot-based; human networked multiplayer is not included.
- 2Fort supports complete authored 24-player RED-versus-BLU local Capture the Flag matches.
- Upward retains its authored map, entities, bots, combat, round state, and navigation, but its complete physics-driven Payload cart and breakable constraint are not implemented.
- Engineer stock buildings, construction/destruction menus, placement restrictions, and wrench upgrades are available.
- Demoman's Bottle is playable, but the Stickybomb Launcher and fully simulated pipe-grenade trajectories remain unavailable until exact Source rigid-body behavior is complete.
- Browser WebGPU cannot expose application-controlled display synchronization; the VSync setting is therefore capability-gated rather than fabricated.
- Only `jump_beef`, `pl_upward`, and `ctf_2fort` are configured release maps.
