# TF2 Jump Roadmap

[`../../../../docs/roadmap-contract.md`](../../../../docs/roadmap-contract.md) defines the normative roadmap schema and denominator review gate. [`../../../../TERMINOLOGY.md`](../../../../TERMINOLOGY.md) defines delivery status, coverage classification, inventory, evidence, and completion terms.

## Completion Denominator

This leaf roadmap contains exactly 38 behavior rows. [`inventories/course-behaviors.md`](inventories/course-behaviors.md) contains 117 candidate zone, topology, eligibility, fixed-policy, loadout, explosive-cleanup, run-transition, and result-output items. Those candidates contribute 0 denominator items until a checked-in generator emits the inventory and a denominator review accepts it. [`inventories/jump-beef.md`](inventories/jump-beef.md) pins 49 fixed public zone identities as target evidence; dynamic map records are inputs, not denominator items. The current completion denominator is therefore 38 behavior rows. Acceptance of all 117 candidate inventory items without a roadmap change would make the denominator 155 items.

The denominator covers TF2 jump mode rules only: immutable course definitions; linear and staged map courses; bonuses; zone contacts; player eligibility; Soldier and Demoman policy; loadout decisions; per-player run state; starts; checkpoints; timer ticks; invalidation; reset; restart; death; respawn; map teleport effects on runs; target-defined save/restore; completion; result facts; owned-explosive cleanup requests; map-entity integration; multiplayer isolation; and the output seam consumed by the Tempus application.

The denominator is Not accepted. The candidate inventory has no generator or review record; the TF2 ruleset-universe inventory and Jump assignment are candidate-only; the exact `jump_beef` zone bounds and zone-to-contact mapping are unavailable; exact checkpoint, invalidation, reset, restart, death/respawn, save/restore, trick-zone, and multiplayer-interaction contracts are unavailable; and required TF2 and generic package interfaces are not accepted.

## Inputs

- One immutable `JumpCourseDefinition` with stable identity and content hash: canonical map identity; topology equal to `linear` or `staged`; ordered zone definitions; course, bonus, checkpoint, and accepted trick identities; class/team/loadout policy identity; and every required relation between start, checkpoint, and end zones. Map catalog metadata, records, ranks, and presentation fields are not part of this value.
- Each zone definition contains one stable zone identity; one inventory kind; positive index where applicable; immutable Collision shape reference; optional name bytes; enabled state; and explicit topology relations. Jump receives ordered Entity contact facts and never performs overlap geometry.
- One immutable prior `JumpState`: course-definition identity; one player entry per Simulation player; eligibility snapshot; active/completed/invalidated run instances; exact start and visit ticks; ordered checkpoint visits; reset/restart state; and save state only after its blocked target contract is accepted.
- One ordered tick input containing Simulation tick and exact binary32 interval bits; admitted jump commands; TF2 lifecycle, class, team, loadout, health, death, respawn, projectile, and teleport facts; Movement results; Entity start/end contacts and I/O facts; and package failures. Render-frame time, wall-clock time, network arrival time, and API timestamps are invalid inputs.
- One required limits record containing positive finite `maxPlayers`, `maxZones`, `maxCourses`, `maxBonuses`, `maxCheckpoints`, `maxRunInstancesPerPlayer`, `maxCheckpointVisitsPerRun`, `maxCommandsPerTick`, `maxEventsPerTick`, `maxSavedStatesPerPlayer`, `maxSnapshotBytes`, and `maxDiagnostics`. No operation has an unbounded mode and no field has an implicit default.
- One exact TF2 policy adapter exposing only mode-owned decisions and typed requests. TF2 remains the owner of class, item, loadout, weapon, projectile, damage, movement specialization, respawn, filter, spawn-room, teleport, and entity behavior.
- Valve Source SDK 2013 commit `88fa198fba3fb85d46d4c95018254693fdc3af0a`: TF2 player/class, item/attribute, weapon/projectile, damage/impulse, game movement, respawn, spawn-room, filter, and catapult code; generic `triggers.{h,cpp}`, `filters.{h,cpp}`, base entity I/O, and event queue contracts.
- Tempus public API v0 OpenAPI bytes retrieved 2026-07-18, SHA-256 `3d7bf3b65d4e74a2ae3b12f5c6b45a1cf003f29b6dc35882cccac12c8eb59d99`; Tempus public plugin commit `d7491f5295fbacee1a63fa6603c52cf585fcac18`; and Tempus public server-policy commit `31171fee1073751a1b1feddc93dfbd327f3d0411`. These establish only the contract identities enumerated in the candidate inventory.
- One fixed `jump_beef` public API capture in [`inventories/jump-beef.md`](inventories/jump-beef.md): 8,004 response bytes at SHA-256 `24d6f390d2d7b5eeb7ab46323ce770b88506aa1b7fc739d2c4d9e5c5d4518b83`, with 49 zone identities in a 3,857-byte canonical subset at SHA-256 `b140813677b5b1b64777500b6ac972d5008338d39120b64db4eb75018bb827f5`. It supplies identities only; it supplies no geometry, trigger mapping, topology edge, or transition rule.

## Outputs

- One immutable next `JumpState` containing every accepted run, checkpoint, validity, reset/restart, and save-state transition for the tick. Unchanged TF2 and package state remains referenced by identity and is never copied into a second authority.
- One ordered `JumpEventBatch`: run started, checkpoint accepted/rejected, stage completed, map completed, bonus completed, run invalidated, reset/restart requested, and structured failure. Every event contains course identity, player identity, tick, run kind/index, event sequence, and exact owner-defined payload.
- Typed TF2 requests for ruleset-approved class/loadout policy, forced respawn, health policy, owned-projectile removal, or other accepted mode effects. Jump never mutates TF2 state directly.
- One immutable `JumpRunResult` containing every accepted `result.*` item in [`inventories/course-behaviors.md`](inventories/course-behaviors.md). It is an application input, not a Tempus record, ranking, demo, tier, rating, or database identity.
- One complete Jump snapshot section sufficient to restore every owned state bit and reproduce the next Jump transition against the same course definition, TF2 snapshot, package snapshots, limits, and tick identity.
- A structured failure containing course-definition identity, map identity, player identity, simulation tick, run identity, zone/contact/command identity, violated invariant, offending value, configured limit, and exactly one `Malformed`, `Unsupported`, `Unknown`, or `Missing` classification. Failure publishes no partial Jump state or result.

## Invariants

- Simulation is the sole gameplay authority. Jump advances only during its declared Simulation participant phases and cannot advance a timer, contact, run, or reset from a render frame, application callback, network delivery, or replay timeline.
- One course definition is immutable for one Simulation identity. A changed map, zone, topology, policy, limit, TF2 content identity, or authority revision creates a different definition identity and cannot reuse run state or evidence.
- Jump is selected explicitly from the accepted ruleset composition with an accepted map and course definition. Filename prefixes and unrelated map entities never select it. Jump has no opposing-team objective, overtime, or stalemate transition.
- A zone identity maps to exactly one accepted inventory kind and one Collision shape reference. Zone names never create behavior. Duplicate identities, indices, or conflicting topology edges are Malformed.
- Zone geometry and contact truth come only from Collision and Entity. Jump consumes stable ordered start/end facts; it does not sample AABBs, trace player hulls, infer tunnelling, or maintain a second overlap set.
- Each run instance belongs to exactly one player, course definition, run kind, and index. Another player's commands, contacts, projectiles, reset, death, disconnect, completion, or application state cannot mutate it.
- Elapsed time is integer simulation ticks. Seconds are derived from elapsed ticks and the exact Simulation interval bits. Floating wall time, render interpolation, demo clip boundaries, and API timestamps cannot alter a run result.
- One contact episode starts, visits, or ends a run at most once. Repeated stays and duplicate contact records are inert after the first accepted transition; ordering uses the Simulation/Entity global sequence.
- A completed or invalidated run is immutable. Restarting creates a new run instance; no late checkpoint, map I/O event, projectile event, or application response can repair or rewrite a terminal result.
- Mode resets are atomic across Jump state and emitted TF2 requests. Either run disposition, destination policy, explosive cleanup, health/gravity policy, velocity policy, and next state all commit, or none commit.
- Soldier and Demoman physical behavior is exclusively TF2-owned. Jump selects only the accepted class, team, item, cvar, and cleanup policies enumerated by its inventory.
- Product persistence can accept a committed `JumpRunResult`; it cannot decide whether gameplay started, remained valid, reached a checkpoint, completed, or elapsed for a different number of ticks.
- Every inventory identity receives one coverage classification. Unknown zone meaning, item policy, invalidation cause, save field, or multiplayer interaction remains visible and cannot become an allow decision.
- Every count, visit, command, event, result, snapshot byte, and diagnostic is checked against the immutable limits before mutation or allocation. Truncation is never success.
- No fallback timer, alternate zone sampler, duplicate course authority, compatibility branch, legacy state, ambient mutable cvar read, or stale inventory is permitted.

## Ownership Exclusions

- [`../../ROADMAP.md`](../../ROADMAP.md) owns all TF2-wide mechanics. Jump owns only when and whether a course transition requests those mechanics.
- Movement, Entity, Simulation, Collision, and Physics remain game-independent package owners. Jump consumes their current outputs and cannot embed a movement step, trace, overlap test, event queue, physics solve, or tick loop.
- [`../ROADMAP.md`](../ROADMAP.md) aggregates the finite TF2 ruleset universe and assigns Jump once. It does not own these leaf rules.
- The Tempus application owns map discovery, course metadata acquisition, records, rankings, tiers, ratings, demos, APIs, UI, and product persistence. It consumes Jump outputs without becoming gameplay authority.
- Networking owns transport and reconciliation; Replay owns recorded-state advancement; presentation packages and applications own HUD, effects, audio, and pixels.

## Behavior Families

The tracked playable-runtime checkpoint implements a synthetic local linear-course slice through one ruleset module: caller-supplied Entity contacts; RED/BLU Soldier/Demoman eligibility; entry-edge start; dense ordered checkpoints; completion after all required checkpoints; integer-tick elapsed time; terminal result facts; duplicate/stay suppression; and invalidation plus TF2-owned projectile-cleanup/respawn requests for reset, respawn, class/team loss, and noclip. It is not Tempus parity. The current `jump_beef` caller reclassifies BSP `trigger_multiple` hint/text entities as one start, 19 checkpoints, and one end, while the fixed public target has three course identities, two course-end identities, six checkpoint identities, one map pair, one bonus pair, two tricks, and no linear marker. No public authority maps those Tempus zones to BSP entity ordinals. The runtime does not resolve reset/restart/save/restore/trick/multiplayer policy cells.
