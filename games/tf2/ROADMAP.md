# TF2 Game Roadmap

[`../../docs/roadmap-contract.md`](../../docs/roadmap-contract.md) defines the normative roadmap schema and denominator review gate. [`../../TERMINOLOGY.md`](../../TERMINOLOGY.md) defines delivery status, coverage classification, inventory, and completion terms.

## Completion Denominator

This leaf roadmap contains exactly 62 behavior rows. The nine candidate inventories contain 21,206 class, item, attribute, weapon/presentation, entity, objective, condition, cvar, and network/prediction/event/message items. They contribute 0 denominator items until checked-in generation emits them and a denominator review accepts them. The current completion denominator is therefore 62 behavior rows. Acceptance of all 21,206 candidate inventory items without a roadmap change would make the denominator 21,268 items.

The denominator covers TF2 behavior over generic Source packages: nine playable classes; player, team, class, item, loadout, attribute, condition, health, damage, ammo, weapon, projectile, building, movement-specialization, respawn, entity, objective, game-rule, prediction, replicated-state, replay-interpretation, event, user-message, and game-specific presentation-mapping behavior. Mode lifecycle, scoring, restrictions, and completion belong to [`rulesets/ROADMAP.md`](rulesets/ROADMAP.md).

The denominator is Not accepted. No inventory has a generator or review record; the TF2 ruleset universe is absent; required generic package interfaces are not accepted; and no arithmetic profile or field-specific comparison tolerance has been accepted.

## Inputs

- One immutable prior TF2 state with stable simulation tick and entity identities: player lifecycle, team, class, class data, health/overheal, ammo/metal, loadout, item instances, attribute providers/cache state, conditions and sources, active/last weapons, clips/reload/attack timers, projectiles, buildings, pickups, TF2 entity extensions, objective primitives, common game-rule state, prediction state, and replicated-field source values.
- One ordered admitted-command set supplied by Simulation for the tick. Each player command contains the canonical movement and weapon-selection/attack fields accepted by Simulation and Networking. TF2 validates game eligibility and emits state/events; it does not decode transport bytes or schedule ticks.
- One positive finite fixed tick interval, simulation time, deterministic random stream identity/state for every TF2 random decision, and one immutable validated snapshot of every consumed item in [`inventories/cvars.md`](inventories/cvars.md).
- One selected TF2 ruleset policy containing only mode-owned decisions: lifecycle phase, spawn permission/timing, class/loadout restrictions, objective eligibility/scoring/completion, overtime, and win conditions. TF2-wide mechanics cannot be overridden through this policy.
- One exact content-build input: configured class records, `scripts/items/items_game.txt`, its signature, `resource/modevents.res`, models, weapon scripts, sounds, particles, and animation metadata resolved through Content with logical path, provider identity, source location, and SHA-256 hash.
- Generic package interfaces: Movement state/results; Collision queries; Physics bodies/contacts; Entity state, I/O, triggers, parenting, and mover requests; Simulation ordering/publication; Networking commands/snapshots; Replay decoded records; Material surface properties; and typed Rendering, Particle, and Audio requests. TF2 never substitutes a second implementation for these packages.
- Valve Source SDK 2013 commit `88fa198fba3fb85d46d4c95018254693fdc3af0a`: TF2 shared, server, and client game code under `src/game/{shared,server,client}/tf`; generic `src/game/shared/econ`; generic teamplay/player/weapon/entity code inherited by TF2; and the exact symbols and paths named by the nine inventories.
- TF2 content build `10822003`: `steam.inf` SHA-256 `b8d7c1eb4517a806d514087facf42e3d8f407bf14393ac5fdc5d4c69e40adc7f`; `gameinfo.txt` SHA-256 `a85196fdeebeb4e2bae9d412862794d18a4970d118ea0a0d84817c44b8c982da`; `scripts/items/items_game.txt` SHA-256 `47900e0d174971625a76625fe311a012910031171d0b121ff5f628078c83214d`; `tf2_misc_dir.vpk` SHA-256 `63f7db0d1c509e303ca9002fee9e3d805e9220ea5afdd639d8a6b68b8a3710b9`; and `tf.fgd` SHA-256 `e8985f85da985c11e22e4a68b8ea5031bf775f3f471a8d5d4db622e1e7204a49`.

## Outputs

- One immutable next TF2 state containing every advanced game-owned field and stable references to unchanged generic state. It is suitable for authoritative publication, prediction storage, deterministic evidence, and replay comparison.
- One ordered TF2 gameplay-event journal: class/team/lifecycle changes; item/loadout/attribute/condition changes; damage/healing/death; ammo and weapon actions; projectile/explosion/impulse facts; building changes; pickup/entity/objective/common-rule facts; and typed ruleset requests.
- One canonical TF2 replication source and prediction result containing every accepted logical item in [`inventories/networked-state.md`](inventories/networked-state.md), without network encoding or transport state.
- One ordered game-event and user-message journal with exact typed payloads. Presentation-only messages cannot mutate gameplay state.
- Typed TF2 presentation requests selecting model/skin/bodygroup, animation/viewmodel activity, particle effect, and script sound from authoritative or replay facts. Rendering, Particle, and Audio execute those requests without feeding results back into gameplay.
- A structured failure containing operation, simulation tick, entity/player identity, inventory stable identity, input field or package-query identity, violated invariant, offending value, configured limit, and exactly one `Malformed`, `Unsupported`, `Unknown`, or `Missing` classification. Failure publishes no partial authoritative next state.

## Invariants

- Simulation is the sole gameplay authority. TF2 advances only game-owned state inside an admitted fixed tick; rendering, replay, networking transport, applications, and presentation systems cannot independently advance or repair gameplay.
- Nine and only nine playable class identities are accepted. Team gameplay identities are RED and BLU; unassigned, spectator, auto-assign, Halloween, PvE aliases, Civilian, random, and enum sentinels retain explicit non-playable dispositions.
- Every content-derived lookup binds the configured content build and exact source hash. A changed class record, schema, event file, model, sound, particle, or animation input creates a different evidence target and cannot reuse stale output.
- Item-schema processing preserves source order and duplicate occurrence, resolves prefabs before dependent item definitions, validates cross-references, and never falls back to hardcoded item behavior when a required definition is missing or malformed.
- Attribute application uses one provider graph and one accepted order for local attributes, providers, owner propagation, type conversion, caching, and invalidation. A provider is applied at most once per hook query and cycles fail without partial output.
- Conditions retain numeric identity, source/provider identity, duration or permanent state, add/remove ordering, expiry behavior, prediction state, and presentation facts. Mode-specific grant policy cannot redefine a condition's TF2-wide effect.
- Health, overheal, healing, damage, crit/minicrit, resistance/immunity, death, impulse, and post-damage effects advance in one declared order. Damage randomness consumes only the supplied deterministic random stream and records every draw identity.
- Weapon switching, deployment, holstering, attacks, clips, reserve ammo, reload states, charge states, projectile creation, impact, explosion, deflection, and item meters use simulation time. Render-frame time and animation sampling cannot unlock or delay gameplay actions.
- Collision, movement, rigid-body, mover, trace, and line-of-sight truth come only from the owning generic package snapshot. TF2 selects masks, groups, eligibility, and response policy but cannot perform an alternate mesh ray, hull sweep, or physics solve.
- Building placement, construction, upgrade, repair, damage, sap, carry, redeploy, detonation, and destruction preserve one owner/builder, object identity, object type/mode, upgrade level, health, ammo, and state machine. Sentry, dispenser, and teleporter specializations cannot bypass shared building state.
- TF2 objective entities produce typed primitive state and requests. A mode-specific ruleset exclusively owns lifecycle, objective eligibility beyond the primitive's TF2 contract, scoring, restrictions, overtime, completion, and win decisions.
- Authoritative and predicted execution call the same TF2 transition implementation. Identical prior state, commands, ruleset policy, content identity, package results, cvar snapshot, tick context, and random state produce identical serialized next state and journals under the accepted arithmetic profile.
- Replicated fields are derived from canonical TF2 state once per publication boundary. Demo/replay interpretation maps decoded recorded fields to TF2 meaning and never resimulates missing gameplay.
- Presentation mappings are pure functions of canonical TF2, replay, and immutable content state. Particle lifetime, audio playback, animation interpolation, viewmodel sampling, visibility, and frame rate cannot affect gameplay or replay truth.
- Every inventory identity receives exactly one coverage classification. Unknown, malformed, missing, unsupported, duplicate, owner-conflicting, and excluded discoveries remain visible and cannot be silently dropped.
- Fixed gameplay counts and sentinels come from the accepted inventories and cvar snapshot. Simulation and generic packages own execution-time, memory, queue, entity-count, contact-count, and network backpressure bounds.
- No fallback implementation, compatibility layer, legacy schema branch, duplicate game authority, stale inventory, or ambient installation discovery is permitted.

## Ownership Exclusions

- KeyValues, VPK, StudioModel, BSP, VTF, VMT, PHY, and Demo own format parsing. Content owns logical-path/provider resolution. TF2 owns interpretation of successfully parsed TF2 game content.
- Movement owns generic command movement, hull motion, ground/air/water/ladder/noclip/observer/toss behavior, stepping, and clipping. TF2 owns class/condition/item/weapon movement policy, air dashes, bunnyhop cap, backward clamp, TF2 duck/water differences, charges, grappling hooks, parachutes, rocketpack, karts, ghosts, lost footing, collision groups, and movement events.
- Collision owns geometric queries and trace truth. Physics owns rigid bodies, persistent contacts, constraints, and solver response. Entity owns generic state, I/O, parenting, trigger/touch lifecycle, mover advancement, and rollback publication. TF2 owns game-specific filters, masks, eligibility, damage, and typed responses.
- Simulation owns command admission, fixed-tick scheduling, random-stream provisioning, transition ordering boundary, gameplay publication, and session lifecycle. Networking owns command/snapshot encoding, transport, tables, baselines, deltas, acknowledgement, recipients, and reconciliation mechanics.
- Replay owns recorded-byte decoding and timeline advancement. TF2 owns semantic interpretation of decoded TF2 classes, fields, events, user messages, entities, items, and conditions.
- Rendering, Particle, and Audio own presentation execution. TF2 owns the mapping from TF2 facts to model/skin/bodygroup, animation/viewmodel, particle, and sound requests.
- [`rulesets/ROADMAP.md`](rulesets/ROADMAP.md) owns every mode-only lifecycle, objective, scoring, spawn, restriction, overtime, completion, win, and mode-state transition. TF2 owns reusable mechanics and objective primitives consumed by those rulesets.
- Applications own input bindings, browser UI, HUD layout, menus, settings storage, catalog experiences, and product assembly. Services own hosted processes and transport endpoints. Tempus owns records, courses, rankings, APIs, and product data.
- Store, market, trading, crafting, loot selection, account inventory persistence, matchmaking, tours, contracts/quests, and social progression are excluded from TF2 gameplay advancement. Their schema records remain classified inputs and cannot acquire gameplay meaning implicitly.
- Achievement award logic and bots/AI are excluded because no Active product target declares them as required behavior. Map/entity/item/event fields that mention either remain classified and inert or delegated; adding either target requires a denominator change before implementation.
- Source 2, undeclared games, vehicle driving, NPC locomotion, product-specific camera/UI behavior, legal/publication classification, and content acquisition are excluded.

## Behavior Families

The active migration checkpoints implement one deterministic local TF2 jump-combat session over Movement/Collision: Soldier/Demoman class state, stock rocket/Original and stickybomb firing, fixed fire intervals, projectile advancement, eight-sticky retention, arming/detonation, radius damage, self-damage, blast impulse, health, respawn, and ordered presentation events required by `jump_beef`. The game-owned WASM binding compiles the direct BSP into that session, advances one 24-byte command for a bounded 1 through 64 ticks, and emits a generation-bound versioned binary snapshot without moving game behavior into Map. Its browser adapter stages candidate sessions, verifies cold or warm canonical payload bytes, atomically activates one generation, and exchanges only coarse transferable map/snapshot buffers.
