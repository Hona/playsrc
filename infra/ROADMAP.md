[`../TERMINOLOGY.md`](../TERMINOLOGY.md) defines Infrastructure, delivery statuses, coverage classifications, Bound, and Complete. [`../docs/roadmap-contract.md`](../docs/roadmap-contract.md) defines denominator, inventory, evidence, and review requirements.

The denominator review state is Draft. No acceptance record exists.

## Inputs

- Accepted deployment-requirement manifests from `apps/web/tf2`, `apps/web/tempus`, `apps/services/api`, and `apps/services/assets`. Each manifest names its application build, process or static-output target, public and private listeners, protocols, health checks, configuration identities, secret identities, dependency identities, resource bounds, scaling policy, availability target, telemetry contract, and lifecycle.
- The Active and Future target lifecycle, application ownership, four declared `playsrc.online` hostnames, and canonical browser-product paths from the root roadmap and architecture.
- An accepted Asset Store remote-adapter capability manifest and Asset Service origin, immutable raw/derived object, HTTP range, cache, metadata, request-bound, and observability contract.
- One environment manifest per declared environment containing stable identity, lifecycle, isolation scope, provider account or project, state-backend identity, location set, DNS authority, deployment identity, runtime identities, cost limit, and teardown policy. A local manifest contains no provider credentials or provisioned cloud resources.
- One resource manifest per accepted inventory item containing stable semantic identity, sole owner, environment, provider kind and locked revision, dependency identities, network exposure, capacity and scaling bounds, configuration-binding identities, secret-reference identities, telemetry requirements, backup and restore policy, deletion protection, and cost attribution.
- Locked infrastructure engine and provider revisions, a conditionally updated remote state backend, an approved plan digest, caller identity, cancellation signal, and operation elapsed-time bound.
- Decommission authorization identifying the exact environment, accepted inventory revision, resources permitted to be removed, persistent resources that must remain protected, and every owning data service's prerequisite result.

## Outputs

- A validated resource-and-environment inventory with one stable identity, lifecycle, owner, environment, dependency set, and coverage classification per item.
- A deterministic plan containing the authority revisions, engine and provider revisions, prior state revision, desired-definition digest, ordered `Create`, `Update`, `Replace`, `Delete`, and `NoOp` actions, protected-resource refusals, cost delta, and plan digest. Planning performs no provider mutation.
- An apply report containing the approved plan digest, caller identity, ordered attempted actions, provider operation identities, resulting state revision, verification results, elapsed time, and exact terminal outcome.
- Environment binding output containing only public endpoints, resource identities, configuration-reference identities, secret-reference identities, and provider capability identities. Secret values never enter definitions, state, plans, outputs, logs, or evidence.
- Drift, backup-readiness, restore-exercise, teardown, capacity, scaling, access-policy, and cost-control reports keyed to exact inventory and provider revisions.
- Failures use exactly these error kinds: `MalformedDefinition`, `UnknownEnvironment`, `UnknownResource`, `OwnershipConflict`, `MissingRequirement`, `DependencyCycle`, `ProviderCapabilityUnavailable`, `StateConflict`, `PlanStale`, `PolicyDenied`, `SecretUnavailable`, `CapacityExceeded`, `ApplyFailed`, `VerificationFailed`, `DriftDetected`, `ProtectedResource`, `TeardownFailed`, `CostLimitExceeded`, and `Cancelled`.

Resource observed state is exactly `Absent`, `Converged`, `Drifted`, `Protected`, or `Failed`. An operation report is not resource state and cannot hide a provider-side partial result.

## Invariants

- Checked definitions can create or configure only accepted inventory items. Unknown, unowned, Future, duplicate, or cross-environment items fail before planning.
- `local` and the bounded TF2 `production-poc` Cloudflare deployment are the currently declared execution environments. Development, staging, and production Channel names do not declare additional hosting environments. Another hosted environment enters the inventory only through an Accepted application or service requirement.
- Active requirements and Future requirements remain disjoint. Future CS:S, legacy Source 1 CS:GO, matchmaking, game-server, and `servers.playsrc.online` resources cannot be provisioned before their root lifecycle changes to Active and their deployment requirements are Accepted.
- Stable semantic identities never depend on provider-generated names, creation time, list order, or mutable endpoint values. Provider names are deterministic collision-free mappings recorded in state.
- Planning is read-only and byte-identical for the same definitions, inventory, state revision, engine revision, provider revisions, and provider observations after nondeterministic provider fields are normalized explicitly.
- Apply accepts exactly one approved plan digest. A changed definition, inventory, state, provider lock, policy, or observed prerequisite makes the plan stale and causes zero planned mutation.
- Creation and update order is identities, access policy, and parent DNS authority; network and data resources; logs and metrics; origins and compute; health verification; certificate validation, TLS, CDN, and routes; traffic DNS; then alerts and dashboards. Teardown removes traffic DNS and routes first and then proceeds in reverse dependency order.
- An apply failure stops dependent actions, records every completed and failed provider operation, preserves the prior checked state revision until reconciliation, and never selects a fallback provider, region, endpoint, resource, or application build.
- Every environment has a distinct provider isolation scope, state identity, deployment identity, runtime identities, network policy, configuration bindings, telemetry labels, and cost attribution. No mutable state, credential, route, secret, or resource reference crosses environments.
- Public ingress is denied unless an accepted application listener and route require it. Administrative, state-backend, object-origin, data, and secret access is private and deny-by-default.
- Infrastructure provisions remote storage, CDN, identities, and bindings without interpreting object bytes, mutating immutable published objects, choosing Channel targets, replacing Channel records, or treating CDN responses as storage truth.
- Databases and queues do not exist unless an Accepted service roadmap names their data model or message contract, consistency, retention, capacity, backup, restore, and lifecycle requirements.
- Secret values are supplied only at runtime by the selected secret provider to the named identity. Missing, unauthorized, stale, or cross-environment secret references fail closed.
- Logs, metrics, alerts, and dashboards use the same environment, application, service, route, resource, operation, and deployment identities. Telemetry contains no secret values or request bodies unless an Accepted application contract explicitly classifies a bounded field as safe.
- Every capacity, concurrency, queue-depth, request-rate, storage, retention, replica, autoscaling, retry, operation-time, and cost limit is numeric and immutable within one approved plan. Reaching a limit invokes the declared reject, delay, or scale action and never silently raises the limit.
- Backups apply only to mutable data whose accepted owner requires recovery. Immutable asset objects use retention and integrity verification, not backup mutation; Channel target selection and rollback remain Asset Store behavior.
- Teardown cannot delete or overwrite immutable asset objects, select a Channel target, bypass deletion protection, remove a required backup, or destroy shared DNS authority or state while an accepted environment still depends on it.
- One current engine, provider set, state shape, naming contract, and resource definition exists. No compatibility branch, legacy reader, provider fallback, or imperative out-of-band setup can satisfy a row.

## Ownership Exclusions

- `apps/web/<product>` owns product routes inside the application, browser behavior, static-output or process requirements, application configuration schema, build identity, and application-specific deployment configuration. Infrastructure consumes an Accepted deployment manifest and owns provisioned hosting resources and bindings.
- `apps/services/<service>` owns process lifecycle, listeners, transports, authentication behavior, health behavior, request limits, endpoint semantics, and operational telemetry fields. Infrastructure owns compute, network, identity, secret-provider, and observability resources that satisfy those declared requirements.
- `packages/asset-store` owns object identity, immutable writes, reachability, remote synchronization, Channel records, Channel mutation, retention, publication, and rollback. Infrastructure owns storage and CDN provisioning, provider capability bindings, access policy, and environment isolation only.
- `apps/services/assets` owns HTTP asset routes, range behavior, response metadata, cache directives, request bounds, and request observability. Infrastructure configures the origin and CDN to enforce that accepted contract without redefining it.
- `tools/playsrc` owns release, deployment, rollback, and operator-command orchestration. Infrastructure owns plan, apply, drift, and teardown behavior invoked by those commands and never chooses an application build or Channel target.
- Matchmaking owns future queue and session semantics; the game-server service owns future process allocation and draining; gameplay servers own no underlying compute. Infrastructure provisions their compute and network resources only after activation.
- Data-owning services own database schemas, queue message semantics, retention intent, and restore acceptance. Infrastructure owns provisioned data resources, encryption, access policy, backup scheduling, and provider-level restore execution.
- DNS registration, organizational account administration, billing payment methods, application release policy, compilation, asset publication, and gameplay-server process behavior are not Infrastructure behavior.
